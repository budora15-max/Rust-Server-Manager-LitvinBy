# Архитектура проекта

## Обзор системы

Приложение построено на базе Electron и разделено на два изолированных процесса:

* **Main-процесс (`electron/`)** — бэкенд приложения. Отвечает за прямое взаимодействие с ОС: управление процессами Rust, работу с файловой системой, планировщик задач, сетевые сокеты, RCON-клиент, системный трей и push-уведомления.
* **Renderer-процесс (`src/`)** — фронтенд приложения (React SPA на базе Vite). Отвечает исключительно за отрисовку интерфейса, управление локальным состоянием вкладок серверов и отображение графиков.

### Безопасность и изоляция
Рендерер полностью изолирован от Node.js и не имеет прямого доступа к API операционной системы. Все взаимодействие идет строго через безопасный мост в `preload.ts` (`window.rustManager`). Описание типов для контекстного моста находится в файле `src/vite-env.d.ts`.

## Архитектура Main-процесса (Модули)

Вместо монолитного кода логика бэкенда разбита на изолированные модули:

* `main.ts` — точка входа. Отвечает за инициализацию приложения, создание окон, сворачивание в трей и регистрацию всех IPC-обработчиков.
* `rust-process.ts` — жизненный цикл сервера. Запускает и останавливает `RustDedicatedServer.exe`, пишет логи в папки `Logs/server-<id>.log` и подхватывает уже запущенные процессы при перезапуске менеджера. Сюда же встроен Watchdog для авторестарта при зависаниях или крашах.
* `rcon.ts` — клиент WebRcon. Реализует официальный протокол Facepunch (пароль передается в URL) с фолбэком на стандартную команду `rcon.login`. Управляет очередью команд и пингами (heartbeat).
* `metrics.ts` и `metrics-history.ts` — телеметрия. Первый модуль собирает текущие данные через `pidusage` и RCON-команды (`fps`, `serverinfo`). Второй — пакует их в персистентную историю (1 точка в минуту) и хранит до 30 дней для графиков.
* `tasks.ts` — планировщик. Отвечает за тайминги перезапусков, предупреждения игроков, создание бэкапов и автоматический разбан. Вынесен в main-процесс, поэтому работает даже при закрытом интерфейсе.
* `wipe.ts` и `backup.ts` — работа с данными. Модуль вайпов чистит `.map`/`.db` файлы и меняет сид, предварительно туша сервер. Модуль бэкапов создает резервные копии мира с уникальными именами по таймстампу.
* `plugins.ts`, `mods.ts` и `marketplace.ts` — экосистема Oxide. Отвечают за установку самого фреймворка из ZIP-архивов через `adm-zip`, сканирование локальных плагинов, их отключение (через суффикс `.disabled`) и парсинг каталога uMod через `search.json`.
* `config.ts` — парсер `server.cfg`. Отвечает за чтение, сохранение и валидацию конфигов (например, автоматически оборачивает в кавычки параметры, содержащие пробелы).
* `ports.ts` — сетевой аудит. Проверяет занятость портов через утилиты ОС (`netstat`, `tasklist`, `ss`), открывает правила в брандмауэре Windows (запрашивает UAC) и пингует порты по TCP снаружи.
* `notifications.ts`, `telegram.ts`, `discord.ts` — алерты. Отправляют системные пуши в Windows, а также стучат в вебхуки Discord и Telegram при важных событиях.
* `locale.ts` — языковой движок для бэкенда. Нужен для правильной локализации системного трея и текстов уведомлений.

## Контракт IPC (Межпроцессное взаимодействие)

Связь между фронтендом и бэкендом строится по следующим правилам:

1. **Запросы из UI (Invoke):** Обработчики регистрируются в `main.ts` внутри функции `registerIpc`. Имена каналов используют паттерн `домен:действие` (например, `server:start`, `ports:firewall-open`). На стороне рендерера они вызываются через `window.rustManager`.
2. **События от бэкенда (Push/Broadcast):** Для отправки событий в UI используется функция `broadcast(channel, payload)`, которая обернута вокруг стандартного `webContents.send`. Подписки в React-компонентах оформляются через функции вида `onEvent(callback)`, возвращающие метод для отписки (`unsubscribe`).
3. **Дублирование типов:** Типы данных для IPC намеренно дублируются в `electron/types.ts` (для бэкенда) и `src/types/index.ts` (для фронтенда), так как сборка этих частей идет через разные конфигурации `tsconfig`.

> **Правило разработки:** При добавлении любого нового IPC-метода правки вносятся в **4 места**: хендлер в `main.ts`, обертка в `preload.ts`, декларация типов в `vite-env.d.ts` и структуры данных в оба файла `types.ts`.

## Реализация планировщика задач (`tasks.ts`)

* **Хранение:** Список задач пишется в JSON-файл по пути `userData/scheduled-tasks.json`.
* **Жизненный цикл:** Проверка очереди (тик) происходит каждые 15 секунд. 
* **Логика задач:** Для циклических задач (`restart`, `backup`) время следующего запуска (`nextRun`) пересчитывается сразу во время тика. Одноразовые задачи (предупреждение в чат перед рестартом, снятие бана) удаляются из очереди непосредственно перед их исполнением.
* **Тестируемость:** Чтобы модуль можно было покрыть тестами без запуска всего Electron, сами действия инжектируются в планировщик извне через колбэки `TaskActions`.

## Данные и i18n в интерфейсе

* **Управление серверами:** Глобальное состояние живет в `ServerContext`. Список добавленных серверов сохраняется в `localStorage`, а текущие статусы синхронизируются с бэкендом через вызов `server:sync-servers`.
* **Поток метрик:** Живые данные для графиков идут через контекст метрик, а исторические точки запрашиваются при переключении табов через `metrics:history`.
* **Интернационализация:** Переводы интерфейса работают на базе `i18next` (RU/EN). При смене языка на фронтенде отправляется хук `locale:set`, чтобы main-процесс тоже переключил язык системных уведомлений.

## Тестирование

Все тесты вынесены в директорию `tests/` и работают на базе стандартного нативного модуля `node:test` без использования сторонних фреймворков (вроде Jest или Vitest). Тестируются «чистые» модули, не завязанные на окружение Electron (конфиги, порты, планировщик, бэкапы). 

Запуск тестов: `npm test` (скрипт автоматически компилирует файлы бэкенда в папку `dist-electron` перед прогоном).
